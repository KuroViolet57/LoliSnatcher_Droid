# Architecture (1.0)

The app was restructured for 1.0 (October 2026) from seven flat folders under
`lib/src/` into layers and features. Nothing about what the app does changed in
the move; every file kept its name and content (only import lines were
rewritten, checked by `tool/restructure/move_files.py`). The old → new path of
every file is in `tool/restructure/mapping_m1.json`.

The release label is versionName `1.0.0`, versionCode `5211`, codename
`v1.0-rebuild`. Settings → the version row shows `v1.0-rebuild-1.0.0`.
`pubspec.yaml` is `1.0.0+5211`. The version code is the same as r89 so an
in-place install can replace that build, and that build can be put back.

## The layers

```
lib/
  main.dart          entry point (startup sequence, see app/)
  gen/               translations generated by slang (assets/i18n) - do not edit
  models/            plain data: Booru, BooruItem, Tag, TagType, settings enums ...
  core/              what every part of the app needs, with no feature knowledge
    constants.dart
    logging/         Logger, log redaction, perf trace, navigation trace, startup timeline
    network/         DioNetwork (one pooled client, one user agent), proxy/http overrides,
                     downloads to cache, the headless origin page client
    platform/        the native channel (ServiceHandler), secure storage, app lock,
                     permissions, photo picker, SAF file cache, notifications
    settings/        SettingsHandler (settings.json), SourceSettingsHandler
                     (sourceSettings.json), Modular UI switches
    storage/         DBHandler (store.db, vectors.db), DB parts, TagHandler, BooruTagStore
    ui/              generic widgets: buttons, dropdown, flash messages, settings rows,
                     network image + favicon, text, progress, kaomoji ...
    utils/           Tools, extensions, HTML parsing, text parser, debouncer ...
  sources/           one folder per family of sites
    framework/       BooruHandler (the base every source extends), the factory,
                     SiteProfile, post files, reader pages, tag catalog base classes,
                     linked media, site filters
    booru/           classic boorus (danbooru, gelbooru, e621, moebooru, sankaku ...),
                     pools, bakemono's profile, their tag catalogs
    tube/            video sites (hanime1, kusowanka, tik.porn, xxxtik, xxxfollow,
                     redgifs, rule34video) and their catalogs
    furaffinity/     handler, parser, query, session, catalog
    kemono/          kemono.cr / pawchive.pw: site table, API, handler, session,
                     creator index, file host probe
    doujin/          one folder per doujin site (nhentai, ehentai, eahentai, schale,
                     hitomi, hentaipaw, faccina, asmhentai) + common/ (filters,
                     namespaces, listing tag backfill, recommendation engine)
    local/           sources made from the app's own data: downloads, favourites,
                     history, collections, merge, the WebView tab
  features/<name>/
    logic/           handlers and services, no widgets
    ui/              pages and widgets
    accounts  backup  boards  collections  debug  doujin  downloads  feed
    furaffinity  history  kemono  links  recommender  settings  sync  tabs
    tags  video  viewer  webview
  app/               the shell: home (mobile / desktop / loading), side drawers,
                     theme, routing, lock screen, global overlays
```

## The rule

```
models  <  core  <  sources  <  features/*/logic  <  features/*/ui  <  app
```

A file may import its own layer and the layers to its left, never one to its
right. `test/architecture_test.dart` checks every import in `lib/` on every test
run. The imports that broke the rule when the app was restructured are listed in
`test/architecture_allowlist.txt`; that list may only shrink (the test fails on a
new violation and on a listed line that is fixed). `python
tool/restructure/layer_report.py` prints the remaining violations per layer pair.

How to fix one: move the code that is needed down to the lower layer (a model,
a core helper), or let the higher layer hand it in (a callback, a small
interface registered at startup).

## Where does new code go?

| You are adding | Put it in |
|---|---|
| a site | `sources/<family>/`, registered in `sources/framework/booru_handler_factory.dart` and `models/booru_type.dart` (HANDOVER §11) |
| a screen or widget of a feature | `features/<feature>/ui/` |
| the logic behind it (a handler, a store, a service) | `features/<feature>/logic/` |
| a setting | `core/settings/settings_handler.dart` (+ its row in `features/settings/ui/`) |
| a widget with no feature knowledge | `core/ui/` |
| a data class | `models/` |
| something for the shell (drawer, home, theme) | `app/` |

## Tools

| Tool | What it does |
|---|---|
| `tool/flutterw.sh <args>` | runs one flutter command at a time on this PC (two at once hang) |
| `tool/deliver_build.py <token> "<descriptor>" <changes> [--both]` | builds and parks APKs on the K: drive |
| `tool/side_by_side_clone.sh <serial> [--with-cache] [--trust-filter]` | copies the regular app's data into the side-by-side 1.0 install (rooted device) |
| `tool/measure_startup.sh <serial> <package> [runs]` | cold-starts N times and prints the `startup:` timeline |
| `tool/restructure/move_files.py <mapping.json>` | moves files and rewrites every import, verifying nothing else changed |
| `tool/restructure/layer_report.py [--write]` | the layer violations; `--write` regenerates the allowlist |
