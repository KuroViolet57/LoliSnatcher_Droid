# LoliSnatcher 1.0 — the rebuild (design)

Date: 2026-10-04 · Branch: `claude/app-refactor-rebuild-209b44` (from r89, `0bdbd946`) ·
Size: **architectural** (the app's whole skeleton changes) · Mode: one-shot.

## 1. Why, and principles

The app grew over 89 rounds of features bolted onto an upstream codebase. It works,
but its structure no longer matches what it is: 165k lines of Dart in seven flat
folders (`boorus/ data/ handlers/ pages/ services/ utils/ widgets/`), a settings
handler of 3,347 lines that half the app imports, a database handler of 2,920
lines, widgets of 4,500 lines, and logic that reaches into UI and UI that reaches
into everything. The user asked for a 1.0 that is the same app rebuilt "as if it
had been designed from the start": every feature, the UI and every small
behaviour kept, and the result better.

Principles:
1. **Same app.** No visual change, no interaction change, no feature removed, no
   setting renamed or reset, no data format change. The phone's data (settings,
   `store.db`, `vectors.db`, `doujinData.json`, backups) opens unchanged.
2. **New skeleton.** Files live where a newcomer would look for them; layers are
   enforced by a test, not by convention.
3. **Verified moves.** File moves are scripted and checked byte-for-byte; splits
   keep public names (callers compile unchanged or are rewritten by script); the
   1,623 existing tests stay green at every commit.
4. **Better, measured.** Startup time and periodic jank are measured on the Thor
   before and after (`startup:` log line, frame stats), bugs found by the map are
   fixed test-first, the analyzer ends at zero issues.
5. **No upgrades.** No package, Flutter, Gradle or engine version changes (standing
   rule). The vendored `third_party/` copies stay as they are.

## 4. Platform limits (sources)

- Two Android installs cannot share private data; the side-by-side app starts empty
  unless data is copied (`tool/side_by_side_clone.sh`, root only) or restored from a
  backup. Secure storage (Drive link, viewed-changelog marker) is keyed to each app's
  Keystore and is not copied. SAF folder grants are per app.
- Android picks an update by `versionCode` only: the in-place 1.0 must keep a
  `versionCode` ≥ 5211 (r89's). `versionName` may go to `1.0.0`.
- The in-app update checker compares `Constants.updateInfo.buildNumber` with the
  upstream `update.json` (`build_number` 5210): any build number ≥ 5211 never shows
  an "update available" for upstream 2.5.0.
- Two SQLite libraries must never open the same file in one process (POSIX locks are
  per process; https://www.sqlite.org/howtocorrupt.html §2.2.1), so the FFI `sqlite3`
  package is NOT used to speed up reads of `store.db`.
- The test handheld runs AdGuard; newly installed apps get their HTTPS re-signed, so
  the side-by-side copy is made with "Allow self-signed certificates" on.

## 5. Data

Unchanged: `settings.json` keys and value formats, `store.db` schema (tables, columns,
indexes), `vectors.db`, `doujinData.json`, `sourceSettings.json`, session files,
backup file formats and the backup item list. A schema-version marker may be added
to skip repeated DDL (see §7.4); it uses SQLite's `user_version` pragma (currently
1, set by sqflite's `version: 1`), so older builds reading the file are unaffected.

## 6. Architecture (target)

See `docs/ARCHITECTURE.md` (the tree, the rule, where new code goes). Three steps:

1. **M1 move** (done): every file to its layer/feature folder by
   `tool/restructure/move_files.py`, old -> new in `tool/restructure/mapping_m1.json`.
2. **M3 parts**: 25 libraries that hold several declarations are cut into part files
   (`<library>/<part>.dart`, `part of '../<library>.dart'`) by
   `tool/restructure/split_parts.py`; parts share the library's imports and privacy, so
   the program is identical. The proof: the multiset of declaration texts before and
   after is equal. Plans in `tool/restructure/m3_part_plans.json` (dry run: 0 errors).
3. **M3 classes**: the four single giant classes (`SettingsHandler` 3,256 lines,
   `DBHandler` 2,887, `BooruHandler` 1,377, the big doujin handlers) are composed from
   mixins in part files, each mixin one cohesive group (DB: items, collections, history,
   tags, vectors, recommender log, kemono creators...). Public names, members and statics
   stay on the original class, so no caller changes.

The layer allowlist (84 at M1) shrinks where a violation is cheap to cut; the rest stays
documented in `test/architecture_allowlist.txt`.

## 7. Logic and app

### 7.4 Startup

Measured (the `startup:` line, §9): the home screen waits for, in order, the WebView user
agent (~55 ms), settings, models and services (~20 ms), proxy/player registration,
the database (~180-300 ms: open, ~50 schema statements one platform call each, critical
indexes, vectors DB, three maintenance scans), sources, the tag map (~530-640 ms: 128,448
rows from `Tag`, one awaited `putTag` per row), tab restore (~60 ms for 5,063 tabs) and
the migrations. Changes, each measured on the Thor with the same data copy:

1. The WebView user agent is read in parallel and awaited only before the home screen
   (it is needed by the first network request, not by the database or tags).
2. The schema statements go in one `batch` (same statements, same order).
3. `loadTags` fills the map without an `await` per row (the same `putTag` logic, synchronous
   part only, DB writes were already off for this path).
4. `SAFFileCache.populate` asks `hasSafAccess` (no picker, no test file) instead of
   `testSAF` (which writes and deletes a file in the download folder on the main thread -
   and in this Flutter version Dart runs on the main thread).
5. Tab backup every 30 s skips the JSON encode and DB write when a cheap signature of the
   tabs is unchanged (and writes at least every 5 minutes regardless).

Kept: tags before tabs (search-box chip colours on the first frame), the doujin migration
before the home screen, every maintenance step (only moved if measured expensive).
