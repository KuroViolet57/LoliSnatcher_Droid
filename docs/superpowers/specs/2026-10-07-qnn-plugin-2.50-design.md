# QNN plugin EP (QAIRT 2.50) — design

## Why, and principles

Settings → Models → Run on → NPU already sends a session to Qualcomm's HTP
through ONNX Runtime. Commit bce028ed bundled Microsoft's
`onnxruntime-android-qnn:1.29.0`, whose POM depends on `qnn-runtime:2.42.0`,
and called `addQnn`. That is not QAIRT 2.50.

Qualcomm's plugin package is the 2.50 path. Maven
`com.qualcomm.qti:onnxruntime-android-qnn:2.6.0` (checked 2026-10-07,
metadata latest 2.6.0) is a 1,595,551-byte AAR whose only native file is
`jni/arm64-v8a/libonnxruntime_providers_qnn.so`. Its classes jar exposes
`QnnPluginEpLibraryKt.getLibraryPath()` = `libonnxruntime_providers_qnn.so`
and `getEpName()` = `QNNExecutionProvider`. The v2.6.0 provider doc says
this release is validated against:

- `com.microsoft.onnxruntime:onnxruntime-android:1.27.0` (the base package,
  not `onnxruntime-android-qnn`)
- `com.qualcomm.qti:qnn-runtime:2.50.0` (AAR 71,270,746 bytes; 2.42.0 is
  63,074,692)

The same page says the plugin was tested with ORT 1.27.0 and is compatible
with ORT >= 1.24.1. This change pins the validated pair, not a newer ORT
the plugin page does not name. ORT 1.27.0's Java sources still have
`addXnnpack(Map)`, `setSymbolicDimensionValue`, `getDimensionNames`,
`registerExecutionProviderLibrary`, `getEpDevices`, and
`addExecutionProvider(List<OrtEpDevice>, Map)`. They do not have `addArmNN`.

Do not keep `onnxruntime-android-qnn:1.29.0` beside the plugin. Both ship
`ai.onnxruntime` classes. Do not force `qnn-runtime:2.50.0` under the
bundled 1.29 AAR. That AAR was built for 2.42.

## What the user sees

No new screen and no new setting. The existing control is
Settings → Models → a model → Run on → NPU. CPU and XNNPACK stay the other
choices. The page text already says the NPU is the Snapdragon Hexagon
through QNN at 16-bit. It does not name a runtime version, so it stays.

Failure still comes back as a session error the model page already logs.
A missing plugin file or a registration failure does not crash the channel.

## Platform limits, with sources

- Plugin AAR `AndroidManifest.xml` declares `minSdkVersion="27"`. The app
  stays at `flutter.minSdkVersion` (the side-by-side build printed 24).
  Both the plugin module manifest and the app manifest set
  `tools:overrideLibrary="ai.onnxruntime.qnnpluginep"`. Devices below 27
  can still install. They never load the plugin unless Run on is NPU.
- Registration needs a real file. Non-store builds already set
  `useLegacyPackaging` so `nativeLibraryDir` contains the `.so`.
- `libQnnHtp.so` and the skel libraries still come from `qnn-runtime`.
  The app still sets `ADSP_LIBRARY_PATH` to `nativeLibraryDir`. GPU and
  the old DSP libraries stay excluded.
- ProGuard already keeps `ai.onnxruntime.**`.
- Not tried on a phone. A Gen 3 context binary still will not load on the
  Thor's Gen 2. The app still compiles a normal ONNX on first NPU open.

## Data

No schema key, no database change, no backup change. Run on is already
stored and already copied with `settings.json`.

## Logic

On the first session that asks for provider `QNN`:

1. Resolve `nativeLibraryDir/libonnxruntime_providers_qnn.so`. If the file
   is missing, return `QNN_PLUGIN` and do not create the session.
2. If `OrtEnvironment.getEpDevices()` has no `QNNExecutionProvider`, call
   `registerExecutionProviderLibrary("QNNExecutionProvider", path)` once
   for the process. The environment is a singleton, so a second engine
   attach sees the device and does not register again.
3. Pass every device whose `epName` is `QNNExecutionProvider` to
   `SessionOptions.addExecutionProvider`, with the existing QNN option map
   (`backend_path` `libQnnHtp.so`, fp16, high performance).
4. CPU and XNNPACK sessions do not register the plugin and still call
   `addCPU` / `addXnnpack`.

## What is not changed

versionCode 5211, package `com.noaisu.loliSnatcher.v1`, the media surface
cap, video_player 2.11.1, chewie, google_fonts, `tab_pill.dart` 219–220,
and the Dart session option map. ARM_NN stays unsupported.

## Tests

`test/npu_test.dart` pins the three Maven coordinates, forbids
`onnxruntime-android-qnn:1.29.0` and `addQnn(`, and requires
`registerExecutionProviderLibrary(`, `addExecutionProvider(`, the `.so`
name, the EP name, and `tools:overrideLibrary`. The Android plugin
Kotlin compile is the link check. Neither is a run on a phone.

## Assumption register

| ID | Assumption | How it could be wrong | Result | Status |
|---|---|---|---|---|
| A1 | Plugin 2.6.0 loads into ORT 1.27.0 on Android the way the doc says | The Maven AAR could be a stub, or the ABI could reject 1.27 | AAR contains the arm64 provider `.so`; doc names this exact pair | doc-verified |
| A2 | `nativeLibraryDir` holds the `.so` for this app's non-store build | Store packaging turns extraction off | Existing test pins `useLegacyPackaging` for non-store | verified (PC, source) |
| A3 | Registering once per process is enough | A second `OrtEnvironment` could be created | Code uses `getEnvironment()` and skips when the EP device is already listed | guessed until a phone opens two engines |
| A4 | minSdk override does not raise the app to 27 | Merger could still pick 27 | Badging of the next APK must still say sdk 24 | checked on the APK |
| A5 | qnn-runtime 2.50's HTP libraries still honor `ADSP_LIBRARY_PATH` | Skel names could change and the DSP loader would miss them | Not opened on a device | guessed, device checklist |

## Coverage

Parent plan item "QNN toward QAIRT 2.50" is this change. MiniLM-v2 and the
re-verify queue stay later one-shots.

## Delivery

Side-by-side APK, versionCode 5211, not marked tested. On-device check:
set Run on to NPU, run one picture, then set it back to CPU.
