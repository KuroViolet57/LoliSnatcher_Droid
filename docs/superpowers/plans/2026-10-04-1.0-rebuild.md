# Plan: LoliSnatcher 1.0 — the rebuild

**Goal:** the same app (every feature, the UI and each small behaviour kept) rebuilt on a
layered, feature-first skeleton, with verified bug fixes, a faster start and less periodic
jank; delivered as a 1.0 that installs next to build 119 (side-by-side) or over it (in place).

**Architecture:** `docs/ARCHITECTURE.md` (models < core < sources < features/*/logic <
features/*/ui < app, enforced by `test/architecture_test.dart`).

**Tech stack:** Flutter 3.42.0-0.4.pre (beta worktree), Dart 3.12 beta, GetX/GetIt, sqflite,
media_kit (vendored), ONNX Runtime + QNN (vendored). No version changes.

**Spec:** `docs/superpowers/specs/2026-10-04-1.0-rebuild-design.md`. Map:
`docs/superpowers/specs/1.0-map/` (9 subsystem maps: 582 features, 183 suspected bugs, 161
layer findings, 76 split plans, 190 fragile contracts).

## Global constraints

- No package, Flutter, Gradle, Kotlin or engine version changes; `third_party/` untouched.
- `settings.json` keys and value encodings, `store.db` schema, `vectors.db`, `doujinData.json`,
  `sourceSettings.json`, session files and every backup format stay byte-compatible: the phone's
  data (and old backups) must open unchanged. Restore of an r89 backup must work.
- `versionCode` stays 5211 so the in-place APK updates r89 and r89 can be reinstalled over it;
  `versionName` 1.0.0; codename `v1.0-rebuild`. The side-by-side APK is
  `--dart-define=LS_SIDE_BY_SIDE=true` (package `com.noaisu.loliSnatcher.v1`).
- No visual change, no interaction change, no string change unless the string is the bug.
- Every flutter command through `tool/flutterw.sh` (two at once break this PC).
- Credentials never in logs, commits, changelogs (`LogRedaction`); doujin and booru personal
  data never mix (HANDOVER §6.2, `doujin_separation_test`).
- The reader layout contract (`features/doujin/ui/reader/doujin_reader_page.dart` header),
  the r50 viewer swipe, Impeller off, the media_kit pool and `CustomNetworkImage`'s
  headers-by-identity equality are not touched.
- Tests: the full offline suite green after every merge (baseline 1,623 passing + new).
- Never commit: signing changes, local.properties, agent folders.

## Review Focus (most likely to bite a real user first)

1. **Restore and upgrade paths:** an r89 `settings.json`/`store.db`/backup opens in 1.0 with
   every setting and row intact (in-place APK over 119; side-by-side copy). Test:
   `backup_plan_test`, `drive_snapshots_test` + the device check (copy 119's data, compare).
2. **Same event, every path:** bug fixes in favourites/downloads/sync touch shared flows (site
   favourite sync, `toggleFavouriteSynced`, snatch queue). Test per fix + `doujin_separation_test`.
3. **Startup ordering:** tags must be loaded before tabs restore (search-box chip colours on the
   first frame); the doujin migration before the first doujin read. Test: the startup timeline
   order on the device + `startup_timeline_test`.
4. **Moved code changed nothing:** M1 verified by script; M3 splits verified by the declaration
   multiset check and the suite.
5. **Concurrency:** M2 fixes in paging/search (`SearchHandler`, suggestion strips, For You) must
   not introduce double fetches or stuck spinners. Test per fix.
6. **Release-only failures:** R8 keep rules for ONNX/QNN, media_kit, inappwebview after moves
   (class names unchanged; packages unchanged) — the release APK runs on the Thor.
7. **Privacy:** FurAffinity/InkBunny session values and the clipboard (M2 fixes).
8. Every accepted edge case and guessed assumption in the spec's register.

## After the skeleton — feature work

The skeleton above kept the same features, the same UI, and the same
package versions. That is why the diff is moves and bug fixes. On
2026-10-05 the user said that freeze was not their limit: this worktree
exists so the original app stays usable, and this branch may change
packages, the player, the models, the sources, and the UI. `settings.json`,
`store.db`, and `versionCode` 5211 stay compatible so a new APK still
installs over **LoliSnatcher 1.0**. One package or engine change at a time,
each with its own side-by-side APK.

### A — Player, measured before a swap

The app already has four video stacks: vendored `media_kit` 1.2.6 /
`media_kit_video` 2.0.1 (one patch: the Android surface is capped because
an 8K frame cost 600–925 ms and about 2.1 GB), `better_player_plus` 1.2.1,
`video_player` 2.11.1, and `fvp` 0.35.2. GIF playback was a patch on top
of that experiment.

On the Samsung (Snapdragon 8 Gen 3) and the Thor (8 Gen 2), same posts,
mp4, webm, and gif: time to the first frame, dropped frames, memory, heat.
Then either move the vendored mpv libs forward or change the default
engine. The surface cap stays until the new engine does not allocate an
8K surface.

### B — Models that are already compiled for the NPU

Today the app takes a normal ONNX file and compiles it on first NPU open
(QNN, 16-bit) and keeps that copy. It does not download a Qualcomm context
binary. Qualcomm AI Hub publishes compiled models for Snapdragon 8 Gen 3,
8 Gen 2, 8 Gen 1, and 8 Elite
([ai-hub-models](https://github.com/qualcomm/ai-hub-models)). A binary
built for the 8 Gen 3 Hexagon does not load on the Thor's 8 Gen 2.

For the three jobs the app already runs (tagger, text encoder, looks),
find a compiled export for 8 Gen 3 and a separate one for 8 Gen 2. Add
them as presets. The phone picks by chip. The CPU ONNX file stays the
fallback. A diffusion checkpoint is not a tagger.

### C — Sources

Tag builder and favicon, per site. Start from the sites whose tag browser
already says there is no tag index, and the sites whose favicon is wrong
or missing. One site per change, from a captured page. A site with no
public tag list stays listed as unsupported.

### D — WebView

hentaipaw already fetches through a headless WebView. Find the older
scraper prototype in history before adding a second page client.

### E — Downloads, network, snatch, cache, logs

One captured failure (a download or a page) before a stack change. The
trace picks the change.

### F — Themes and the viewer

After A and B. The viewer and the model page are the first screens, unless
